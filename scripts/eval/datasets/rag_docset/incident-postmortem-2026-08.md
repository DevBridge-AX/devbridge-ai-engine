## 상세 분석

### 커넥션 풀 구성

사고 당시 결제 서비스 인스턴스 6개는 각각 최대 33개의 연결을 가질 수 있어 전체 한도는 약 200개였습니다. 정상 시 평균 사용량은 80개 안팎, 피크 시에도 120개를 넘지 않았습니다. 대사용 조회는 한 번 실행에 평균 11분이 걸렸고 동시에 27개 세션이 열리면서 풀의 14%를 점유했습니다. 여기에 실시간 요청의 대기 재시도가 겹쳐 연결 요청이 급증했고, 대기하던 요청이 타임아웃으로 반환되며 클라이언트가 재시도를 보내는 악순환이 생겼습니다.

### 원인 추적 과정

1. 왜 결제가 느렸는가: 요청이 DB 연결을 얻기 위해 평균 1.8초 대기했습니다.
2. 왜 연결이 부족했는가: 풀이 가득 찼고 다수가 장시간 점유 중이었습니다.
3. 왜 점유가 길었는가: 새로 배포된 대사용 조회가 전체 스캔으로 11분씩 실행되었습니다.
4. 왜 전체 스캔이었는가: 조회 조건 컬럼에 맞는 인덱스가 없었습니다.
5. 왜 배포 전에 걸러내지 못했는가: 스테이징 데이터가 운영의 1/200이어서 실행 시간이 수 초에 그쳤고, 실행 계획 점검 절차가 없었습니다.

### 대안 검토

- 롤백 대신 인덱스를 즉시 추가하는 안은 운영 테이블이 커서 인덱스 생성에 40분 이상 걸릴 것으로 보여 채택하지 않았습니다.
- 풀 크기를 즉시 늘리는 안은 DB 서버의 최대 연결 수(400)를 고려해 보류했습니다. 사후에 350으로 조정했습니다.
- 대사용 조회만 끄는 설정 스위치가 없어 전체 버전 롤백이 가장 빠른 선택이었습니다.

### 결제팀
배포 승인 단계에서 새 쿼리 추가 여부를 확인하는 질문이 없었습니다. 체크리스트에 항목을 넣었고, 다음 분기부터 모든 릴리스에 데이터 규모별 실행 계획 첨부를 요구합니다. 또한 커넥션 풀 사용률을 서비스 대시보드 첫 화면에 올려 배포 직후 한눈에 보이도록 했습니다.

### 정산팀
대사 기능은 정산 데이터가 아닌 결제 원장을 직접 조회해 문제가 커졌습니다. 앞으로 대사는 정산 DB의 사본 테이블에서만 수행하며, 결제 원장 조회가 필요한 경우 읽기 전용 복제본을 사용합니다. 복제본이 준비되기 전까지 대사 기능은 비활성 상태로 유지합니다.

### 운영팀
인시던트 선언 기준을 명확히 했습니다. 결제 또는 주문 실패율이 3%를 넘고 10분 이상 지속되면 즉시 선언하며, 선언 전 원인 조사는 최대 10분으로 제한합니다. 지휘자 지정 순서도 온콜 표에 명시했습니다.

### 데이터팀
스테이징 성능 검증용 샘플 복제 작업을 설계 중입니다. 개인정보는 마스킹한 상태로만 복제하며, 복제 주기는 주 1회, 소요 시간은 약 3시간으로 예상합니다.

## 부록: 경보 설정 변경 내역

장애 이후 다음 경보 설정을 바꾸었습니다. 결제 서비스의 DB 커넥션 사용률 경고는 배포 후 30분 동안 75%, 평상시 85%로 이원화했습니다. 대기 중인 연결 요청이 인스턴스당 10건을 넘으면 별도로 경고를 보내며, 이 경고는 사용률과 무관하게 온콜 담당자에게 직접 전달됩니다. 결제 승인 p99 응답이 1,000ms를 3분 넘게 넘으면 치명 경보로 승격합니다.

경보 수신자는 결제팀 온콜과 DBA 온콜 두 명으로 늘렸고, 두 경보 중 하나라도 5분 안에 확인되지 않으면 팀 리드에게 자동으로 에스컬레이션됩니다. 에스컬레이션 대상 목록은 분기마다 갱신합니다.

## 부록: 재현 시도 결과

- 커넥션 사용률: 서비스 인스턴스 전체의 활성 연결 수를 풀 최대 크기로 나눈 값입니다.
- 인시던트 지속 시간: 첫 경보 발송 시각부터 종료 선언 시각까지입니다.
