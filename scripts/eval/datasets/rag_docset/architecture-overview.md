# 서비스 아키텍처 개요

이 문서는 사내 커머스 플랫폼을 이루는 서비스들의 역할과 구성, 운영 기준을 한곳에 모은 개요입니다. 새로 합류한 개발자와 운영 담당자가 전체 그림을 빠르게 이해하도록 작성했습니다.

## 전체 구조

플랫폼은 세 계층으로 나뉩니다. 첫째는 외부 요청을 받는 진입 계층으로 API 게이트웨이와 인증 서비스가 속합니다. 둘째는 업무 계층으로 주문, 결제, 알림, 검색, 파일, 정산 서비스가 있습니다. 셋째는 지원 계층으로 배치 실행기, 리포트 서비스, 감사 서비스, 관리자 콘솔이 있습니다.

서비스 사이의 동기 호출은 사내 네트워크의 HTTP로만 하며, 상태 변화 전파처럼 지연을 허용하는 통신은 메시지 큐 이벤트로 처리합니다. 모든 서비스는 요청마다 `trace_id`를 이어받아 로그에 남깁니다.

## API 게이트웨이 (api-gateway)

API 게이트웨이는 모든 외부 요청의 진입점으로 인증 토큰 검증과 라우팅, 요청 제한을 처리하는 서비스이다. 운영 환경에서 인스턴스 6개로 구성하며 서비스 포트는 8080번을 쓴다. 응답 시간 목표는 p99 기준 120ms이다. 담당 팀은 플랫폼팀이고 데이터는 설정 저장소(읽기 전용)에 저장한다. 게이트웨이는 요청당 상관 ID(trace_id)를 발급하고 라우팅 규칙은 5분마다 다시 읽는다.

### 장애 대응과 상태 확인
- 인스턴스 한 대가 응답하지 않으면 로드밸런서가 30초 안에 대상에서 제외한다.
- 상태 확인 경로는 `/healthz`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 6개 중 절반 이상이 비정상이면 플랫폼팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 2코어, 메모리 4GB이며 부하가 높으면 최대 12개까지 자동으로 늘어난다.
- 주요 의존 대상은 인증 서비스와 설정 저장소이다.
- 배포는 한 번에 한 대씩 교체하며 교체 사이 간격은 90초.

## 인증 서비스 (auth-service)

인증 서비스는 로그인, 토큰 발급과 갱신, 다단계 인증 확인을 맡는 서비스이다. 운영 환경에서 인스턴스 4개로 구성하며 서비스 포트는 8101번을 쓴다. 응답 시간 목표는 p99 기준 90ms이다. 담당 팀은 보안팀이고 데이터는 인증 DB와 세션 캐시에 저장한다. 다단계 인증 코드의 유효 시간은 3분이며 세션 캐시는 노드 3대로 구성한다.

### 장애 대응과 상태 확인
- 세션 캐시 노드가 빠져도 토큰 검증은 서명 확인만으로 계속 동작한다.
- 상태 확인 경로는 `/internal/health`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 4개 중 절반 이상이 비정상이면 보안팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 2코어, 메모리 4GB이며 부하가 높으면 최대 8개까지 자동으로 늘어난다.
- 주요 의존 대상은 인증 DB와 세션 캐시이다.
- 배포는 한 번에 한 대씩 교체하며 새 인스턴스가 토큰 검증 점검을 통과해야 다음 대수로 넘어간다.

## 주문 서비스 (order-service)

주문 서비스는 주문 생성과 상태 전이, 주문 이력 조회를 담당하는 서비스이다. 운영 환경에서 인스턴스 8개로 구성하며 서비스 포트는 8201번을 쓴다. 응답 시간 목표는 p99 기준 150ms이다. 담당 팀은 커머스팀이고 데이터는 주문 DB(주 1대, 복제 2대)에 저장한다. 주문 상태 변경은 이벤트로 발행하고 한 번 발행한 이벤트는 14일간 재조회할 수 있다.

### 장애 대응과 상태 확인
- 주 DB가 응답하지 않으면 주문 생성만 막고 조회는 복제본으로 계속 처리한다.
- 상태 확인 경로는 `/actuator/health`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 8개 중 절반 이상이 비정상이면 커머스팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 4코어, 메모리 8GB이며 부하가 높으면 최대 16개까지 자동으로 늘어난다.
- 주요 의존 대상은 주문 DB, 결제 서비스, 메시지 큐이다.
- 배포는 두 대씩 교체하며 교체 중 주문 이벤트 발행은 멈추지 않는다.

## 결제 서비스 (payment-service)

결제 서비스는 카드와 계좌이체 승인 요청, 재시도, 결제 상태 동기화를 맡는 서비스이다. 운영 환경에서 인스턴스 6개로 구성하며 서비스 포트는 8301번을 쓴다. 응답 시간 목표는 p99 기준 400ms이다. 담당 팀은 결제팀이고 데이터는 결제 DB와 멱등키 저장소에 저장한다. 외부 결제사 호출 타임아웃은 8초로 두고 멱등키는 24시간 동안 저장한다.

### 장애 대응과 상태 확인
- 결제사 응답이 늦어지면 회로 차단기가 열려 60초 동안 새 요청을 대기열로 보낸다.
- 상태 확인 경로는 `/actuator/health`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 6개 중 절반 이상이 비정상이면 결제팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 4코어, 메모리 8GB이며 부하가 높으면 최대 12개까지 자동으로 늘어난다.
- 주요 의존 대상은 결제 DB, 외부 결제사, 멱등키 저장소이다.
- 배포는 카나리로 한 대에 먼저 배포하고 20분 관찰한 뒤 나머지를 교체한다.

## 알림 서비스 (notification-service)

알림 서비스는 푸시와 이메일 발송 요청을 받아 채널별 큐에 넣고 전송하는 서비스이다. 운영 환경에서 인스턴스 3개로 구성하며 서비스 포트는 8401번을 쓴다. 응답 시간 목표는 p99 기준 250ms이다. 담당 팀은 알림팀이고 데이터는 알림 큐와 발송 이력 DB에 저장한다. 발송 이력은 60일 동안 보관하며 채널별 전송 워커는 각각 독립적으로 확장한다.

### 장애 대응과 상태 확인
- 전송 워커가 모두 멈추면 큐에 쌓아 두었다가 복구 후 순서대로 처리한다.
- 상태 확인 경로는 `/status`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 3개 중 절반 이상이 비정상이면 알림팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 2코어, 메모리 4GB이며 부하가 높으면 최대 9개까지 자동으로 늘어난다.
- 주요 의존 대상은 알림 큐, 발송 이력 DB, 외부 푸시 공급자이다.
- 배포는 채널별 워커를 따로 교체하며 이메일 워커가 가장 마지막이다.

## 검색 서비스 (search-service)

검색 서비스는 상품과 문서 검색 색인을 관리하고 키워드 질의에 응답하는 서비스이다. 운영 환경에서 인스턴스 5개로 구성하며 서비스 포트는 8501번을 쓴다. 응답 시간 목표는 p99 기준 200ms이다. 담당 팀은 검색팀이고 데이터는 검색 색인 클러스터(노드 7대)에 저장한다. 색인 갱신 지연은 최대 45초까지 허용하며 이를 넘으면 검색팀 온콜에게 알림이 간다.

### 장애 대응과 상태 확인
- 색인 노드 1대가 빠져도 샤드 복제본 덕분에 질의 결과는 유지된다.
- 상태 확인 경로는 `/_health`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 5개 중 절반 이상이 비정상이면 검색팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 4코어, 메모리 16GB이며 부하가 높으면 최대 10개까지 자동으로 늘어난다.
- 주요 의존 대상은 검색 색인 클러스터, 상품 이벤트 스트림이다.
- 배포는 색인 갱신을 잠시 멈춘 뒤 한 대씩 교체하고 완료 후 밀린 갱신을 이어서 처리한다.

## 배치 실행기 (batch-runner)

배치 실행기는 일 단위 집계, 정리, 내보내기 같은 예약 작업을 실행하는 서비스이다. 운영 환경에서 인스턴스 2개로 구성하며 서비스 포트는 8601번을 쓴다. 예약 작업 위주여서 별도의 응답 시간 목표를 두지 않는다. 담당 팀은 데이터팀이고 데이터는 작업 이력 DB에 저장한다. 동시에 실행할 수 있는 배치는 최대 5개이고 실행 이력은 90일간 보관한다.

### 장애 대응과 상태 확인
- 두 대 중 한 대가 멈추면 남은 한 대가 잠금을 이어받아 미완료 작업을 처음부터 다시 실행한다.
- 상태 확인 경로는 `/jobs/health`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 2개 중 절반 이상이 비정상이면 데이터팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 2코어, 메모리 8GB이며 부하가 높으면 최대 4개까지 자동으로 늘어난다.
- 주요 의존 대상은 작업 이력 DB, 정산 서비스, 리포트 서비스이다.
- 배포는 실행 중인 배치가 없는 시간대에만 교체하며 보통 새벽 04:30 이후에 진행한다.

## 파일 서비스 (file-service)

파일 서비스는 이미지와 문서 업로드, 분할 업로드 조립, 다운로드 URL 발급을 맡는 서비스이다. 운영 환경에서 인스턴스 4개로 구성하며 서비스 포트는 8701번을 쓴다. 응답 시간 목표는 p99 기준 300ms이다. 담당 팀은 플랫폼팀이고 데이터는 객체 스토리지 `file-main` 버킷에 저장한다. 업로드 조각은 5MB 단위로 받고 24시간 안에 조립되지 않으면 정리한다.

### 장애 대응과 상태 확인
- 스토리지 연결이 끊기면 업로드를 거절하고 다운로드는 캐시된 URL로만 허용한다.
- 상태 확인 경로는 `/healthz`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 4개 중 절반 이상이 비정상이면 플랫폼팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 2코어, 메모리 4GB이며 부하가 높으면 최대 8개까지 자동으로 늘어난다.
- 주요 의존 대상은 객체 스토리지, 메타데이터 DB이다.
- 배포는 한 대씩 교체하며 진행 중인 분할 업로드는 다른 인스턴스가 이어받는다.

## 리포트 서비스 (report-service)

리포트 서비스는 정산과 운영 리포트를 생성해 파일로 내보내는 서비스이다. 운영 환경에서 인스턴스 2개로 구성하며 서비스 포트는 8801번을 쓴다. 예약 작업 위주여서 별도의 응답 시간 목표를 두지 않는다. 담당 팀은 데이터팀이고 데이터는 리포트 임시 저장소에 저장한다. 리포트 한 건의 생성 제한 시간은 20분이고 결과 파일은 7일 뒤 삭제한다.

### 장애 대응과 상태 확인
- 생성 중 인스턴스가 중단되면 요청 상태를 실패로 바꾸고 사용자가 다시 요청하도록 안내한다.
- 상태 확인 경로는 `/health`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 2개 중 절반 이상이 비정상이면 데이터팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 4코어, 메모리 8GB이며 부하가 높으면 최대 4개까지 자동으로 늘어난다.
- 주요 의존 대상은 배치 실행기, 리포트 임시 저장소이다.
- 배포는 생성 중인 리포트가 없을 때만 교체하고 있으면 완료까지 최대 20분 기다린다.

## 정산 서비스 (settlement-service)

정산 서비스는 일 정산과 월 정산 집계, 대사, 지급 데이터를 만드는 서비스이다. 운영 환경에서 인스턴스 3개로 구성하며 서비스 포트는 8901번을 쓴다. 예약 작업 위주여서 별도의 응답 시간 목표를 두지 않는다. 담당 팀은 정산팀이고 데이터는 정산 DB(주 1대, 복제 1대)에 저장한다. 집계 결과는 일 단위로 불변 보관하며 정정은 별도 보정 레코드로만 남긴다.

### 장애 대응과 상태 확인
- 집계 도중 DB 장애가 나면 전체 작업을 취소하고 장애 복구 후 해당 일자를 다시 집계한다.
- 상태 확인 경로는 `/actuator/health`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 3개 중 절반 이상이 비정상이면 정산팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 4코어, 메모리 8GB이며 부하가 높으면 최대 6개까지 자동으로 늘어난다.
- 주요 의존 대상은 정산 DB, 결제 서비스 이벤트이다.
- 배포는 일 정산이 끝난 03:30 이후에만 교체하고 월 정산 마감 주간에는 배포하지 않는다.

## 감사 서비스 (audit-service)

감사 서비스는 관리자 행위와 권한 변경 기록을 수집해 변경 불가 저장소에 적재하는 서비스이다. 운영 환경에서 인스턴스 2개로 구성하며 서비스 포트는 9001번을 쓴다. 예약 작업 위주여서 별도의 응답 시간 목표를 두지 않는다. 담당 팀은 보안팀이고 데이터는 `audit-vault` 저장소에 저장한다. 기록은 수신 즉시 서명과 함께 저장하며 적재 지연은 10초를 넘지 않도록 관리한다.

### 장애 대응과 상태 확인
- 적재가 막히면 로컬 디스크 버퍼에 최대 2GB까지 쌓고 복구 후 순서대로 반영한다.
- 상태 확인 경로는 `/healthz`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 2개 중 절반 이상이 비정상이면 보안팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 2코어, 메모리 4GB이며 부하가 높으면 최대 4개까지 자동으로 늘어난다.
- 주요 의존 대상은 감사 저장소, 모든 서비스의 이벤트이다.
- 배포는 한 대씩 교체하며 교체 중에는 디스크 버퍼로 적재를 이어 간다.

## 관리자 콘솔 (admin-console)

관리자 콘솔는 운영자가 설정, 권한, 배포 상태를 조회하고 변경하는 웹 화면과 API를 제공하는 서비스이다. 운영 환경에서 인스턴스 2개로 구성하며 서비스 포트는 9101번을 쓴다. 응답 시간 목표는 p99 기준 500ms이다. 담당 팀은 운영팀이고 데이터는 콘솔 설정 DB에 저장한다. 콘솔의 변경 작업은 모두 감사 서비스로 전송되며 사내 VPN에서만 접속할 수 있다.

### 장애 대응과 상태 확인
- 콘솔이 내려가도 사용자 서비스에는 영향이 없고 운영자는 명령줄 도구로 대체한다.
- 상태 확인 경로는 `/health`이며 로드밸런서가 10초 간격으로 확인한다.
- 인스턴스 2개 중 절반 이상이 비정상이면 운영팀 온콜에게 즉시 알림이 간다.

### 용량과 배포
- 인스턴스 하나의 자원은 CPU 1코어, 메모리 2GB이며 부하가 높으면 최대 3개까지 자동으로 늘어난다.
- 주요 의존 대상은 인증 서비스, 설정 DB, 감사 서비스이다.
- 배포는 업무 시간이 아닌 저녁 20:00 이후에 교체한다.

## 배포 토폴로지

운영 환경은 서울 리전의 세 개 가용 영역에 서비스를 나누어 배치합니다. 상태를 갖는 저장소는 두 개 영역 이상에 복제본을 두고, 상태가 없는 서비스는 세 영역에 고르게 분산합니다. 한 영역 전체가 중단돼도 나머지 두 영역이 전체 트래픽의 100%를 감당하도록 인스턴스 수를 잡았습니다.

## 데이터 흐름 요약

주문이 생성되면 주문 서비스가 이벤트를 발행하고, 결제 서비스가 이를 받아 승인을 요청합니다. 승인이 끝나면 알림 서비스가 고객에게 안내를 보내고 정산 서비스가 다음 일 정산 대상에 포함합니다. 관리자 행위는 어떤 서비스에서 일어나든 감사 서비스로 모입니다.

## 운영 원칙

- 모든 서비스는 무중단 롤링 배포를 기본으로 하며, 배포 절차는 환경별 배포 문서를 따릅니다.
- 설정 값은 코드가 아니라 설정 저장소에서 읽고, 비밀 값은 비밀 관리 도구에서만 주입합니다.
- 용량 점검은 분기마다 하며 CPU 평균 사용률이 60%를 넘는 서비스는 증설을 검토합니다.
- 이 문서의 수치는 분기마다 담당 팀이 갱신합니다.

## 부록: 서비스 간 호출 규칙

서비스가 다른 서비스를 동기 호출할 때는 다음 규칙을 지킵니다. 호출 타임아웃은 호출받는 서비스의 p99 목표의 3배를 넘기지 않으며, 재시도는 멱등한 요청에 한해 최대 2회까지만 합니다. 연속으로 5회 실패하면 호출하는 쪽의 회로 차단기가 열리고, 30초 뒤 한 건씩 시험 호출을 보내 복구 여부를 확인합니다.

의존 관계에 순환이 생기지 않도록 업무 계층의 서비스끼리는 이벤트로만 서로의 상태 변화를 알립니다. 지원 계층의 서비스는 업무 계층을 호출할 수 있지만 그 반대는 허용하지 않습니다.

## 부록: 용량 점검 기록

2026년 3분기 점검에서 결제 서비스와 주문 서비스는 피크 시간대 CPU 평균이 각각 54%와 49%였고, 검색 서비스는 61%로 증설 검토 기준(60%)을 넘어 인스턴스를 5개에서 6개로 늘리는 안을 검토했습니다. 나머지 서비스는 기준 이하였으며 다음 점검은 4분기 마지막 주에 진행합니다.
