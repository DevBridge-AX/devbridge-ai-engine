# API 스타일 가이드

사내 모든 서비스의 공개 및 내부 HTTP API가 따라야 할 설계 규칙입니다. 규칙은 소비자가 API를 예측 가능하게 쓰도록 돕는 것이 목적이며, 서비스별 문서의 수치(요청 한도, 크기 제한 등)가 이 가이드와 다르면 서비스별 문서가 우선합니다.

가이드는 `해야 한다`로 쓰인 항목을 필수 규칙으로, `권장한다`로 쓰인 항목을 선택 규칙으로 봅니다. 예외가 필요하면 아키텍처 리뷰에서 승인을 받고 명세에 이유를 남깁니다.

## 1. 네이밍

- JSON 필드 이름은 snake_case를 사용한다. 예: `order_id`, `created_at`.
- 불리언 필드는 `is_`나 `has_`로 시작한다. 예: `is_active`.
- 배열 필드는 복수형 명사로 짓는다. 예: `items`, `coupons`.
- 약어는 널리 알려진 것(id, url)만 허용하며 사내 약어는 풀어 쓴다.

### 예시와 안티패턴

- 좋은 예: {"order_id": 1024, "is_active": true, "items": []}
- 피해야 할 예: `orderId`처럼 camelCase 필드를 섞어 쓰는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 네이밍 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 2. URL 설계

- 리소스 경로는 소문자 kebab-case 복수 명사를 쓴다. 예: `/v1/order-items`.
- 경로 깊이는 최대 3단계까지 허용하며 그 이상은 쿼리 파라미터로 푼다.
- 동사는 경로에 쓰지 않는다. 다만 취소처럼 상태 전이를 일으키는 동작은 `POST /v1/orders/{id}/cancel` 형태의 하위 경로를 허용한다.
- 경로 끝에 슬래시를 붙이지 않는다.

### 예시와 안티패턴

- 좋은 예: `GET /v1/order-items?order_id=1024`
- 피해야 할 예: `/v1/getOrderItems`처럼 동사를 경로에 넣는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 URL 설계 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 3. 버저닝

- 버전은 URL 경로의 첫 단계에 `/v1`처럼 둔다. 헤더 기반 버저닝은 쓰지 않는다.
- 필드 추가는 하위 호환 변경이므로 버전을 올리지 않는다. 필드 삭제, 이름 변경, 타입 변경은 새 메이저 버전이 필요하다.
- 이전 메이저 버전은 새 버전 공개 후 180일 동안 유지한다.
- 폐기 예정 API는 응답 헤더 `Deprecation`과 `Sunset`에 날짜를 담아 알린다.

### 예시와 안티패턴

- 좋은 예: `Sunset: Sat, 31 Jan 2027 00:00:00 GMT`
- 피해야 할 예: 같은 `/v1` 안에서 필드 타입을 바꾸는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 버저닝 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 4. 에러 응답

- 에러 응답 본문은 `code`, `message`, `trace_id` 세 필드로 구성한다.
- `code`는 대문자 SNAKE_CASE 문자열이며 HTTP 상태 코드와 별개로 업무 의미를 담는다. 예: `FILE_TOO_LARGE`.
- `message`는 사용자에게 그대로 보여 줄 수 있는 한국어 문장으로 쓰고, 내부 구현 정보나 스택 트레이스를 담지 않는다.
- 검증 실패는 400, 인증 실패는 401, 권한 부족은 403, 없는 리소스는 404, 충돌은 409를 쓴다.

### 예시와 안티패턴

- 좋은 예: {"code": "FILE_TOO_LARGE", "message": "파일이 너무 큽니다.", "trace_id": "ab12"}
- 피해야 할 예: 에러 본문에 스택 트레이스를 그대로 담는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 에러 응답 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 5. 페이지네이션

- 목록 API는 커서 방식을 기본으로 하며 `cursor`와 `limit` 파라미터를 받는다.
- `limit`의 기본값은 20, 최대값은 100이다.
- 응답은 `items`와 `next_cursor`를 담고, 마지막 페이지에서는 `next_cursor`를 null로 둔다.
- 총 건수가 꼭 필요한 화면은 별도의 `/count` 경로를 제공한다.

### 예시와 안티패턴

- 좋은 예: {"items": [], "next_cursor": null}
- 피해야 할 예: `page`와 `offset`을 한 API에서 함께 받는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 페이지네이션 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 6. 날짜와 시간

- 시각은 ISO 8601 형식의 UTC 문자열로 주고받는다. 예: `2026-08-19T05:07:00Z`.
- 날짜만 필요한 필드는 `YYYY-MM-DD` 형식을 쓰며 필드 이름을 `_date`로 끝낸다.
- 기간은 시작과 끝을 `from`, `to` 두 파라미터로 받고 끝 값은 포함하지 않는다.

### 예시와 안티패턴

- 좋은 예: `2026-08-19T05:07:00Z`, `settle_date: 2026-08-19`
- 피해야 할 예: 한국 시간 문자열을 시간대 표기 없이 보내는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 날짜와 시간 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 7. 멱등성

- 생성성 요청(POST)은 `Idempotency-Key` 헤더를 받을 수 있어야 한다.
- 같은 키의 요청은 24시간 동안 처음 응답을 그대로 돌려준다.
- 키가 같은데 본문이 다르면 422를 반환한다.

### 예시와 안티패턴

- 좋은 예: `Idempotency-Key: 7f3c0b52`
- 피해야 할 예: 같은 키로 금액이 다른 결제를 허용하는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 멱등성 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 8. 요청 제한

- 모든 API는 분당 호출 한도를 두고 응답 헤더 `X-RateLimit-Remaining`으로 남은 횟수를 알려 준다.
- 한도를 넘으면 429와 `Retry-After` 헤더를 반환한다.
- 내부 서비스 간 호출은 별도 한도를 적용하며, 한도 값은 서비스 문서에 적는다.

### 예시와 안티패턴

- 좋은 예: `X-RateLimit-Remaining: 118`
- 피해야 할 예: 한도 초과 시 500을 반환하는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 요청 제한 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 9. 보안

- 모든 요청은 HTTPS로만 받으며 인증 토큰은 `Authorization: Bearer` 헤더로만 전달한다. 쿼리 문자열로 받지 않는다.
- 응답에 비밀번호, 토큰, 주민번호 같은 민감 값을 담지 않으며 계좌번호는 끝 4자리만 노출한다.
- CORS는 허용 출처를 명시적으로 나열하고 와일드카드를 쓰지 않는다.

### 예시와 안티패턴

- 좋은 예: `Authorization: Bearer <토큰>`
- 피해야 할 예: 토큰을 `?access_token=`으로 받는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 보안 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 10. 문서화

- 모든 엔드포인트는 OpenAPI 명세에 요청, 응답, 에러 예시를 포함해야 한다.
- 변경이 있는 PR은 명세 변경을 함께 올려야 하며 리뷰어는 명세 일치를 확인한다.
- 각 필드에는 한 줄 이상의 설명과 단위를 적는다. 예: 금액 필드는 통화와 최소 단위를 밝힌다.

### 예시와 안티패턴

- 좋은 예: OpenAPI의 `examples` 항목에 성공과 실패 예시를 모두 적는 것
- 피해야 할 예: 구현만 바꾸고 명세는 그대로 두는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 문서화 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 11. 호환성 점검

- 배포 전 계약 테스트로 기존 소비자가 쓰는 필드가 그대로 있는지 확인한다.
- 응답 필드의 의미를 바꿀 때는 이름도 함께 바꾸어 소비자가 변경을 놓치지 않게 한다.
- 열거형 값을 추가할 때는 소비자가 알 수 없는 값을 무시하도록 가이드에 명시한다.

### 예시와 안티패턴

- 좋은 예: 계약 테스트에서 소비자 필드 목록을 비교하는 것
- 피해야 할 예: 필드 의미만 바꾸고 이름은 그대로 두는 것

이 절의 규칙은 새로 만드는 모든 엔드포인트에 적용하며, 기존 API는 다음 메이저 버전에서 맞춥니다. 예외는 호환성 점검 항목에 대해 아키텍처 리뷰 기록으로 남깁니다.

## 가이드 개정

이 가이드는 반기마다 검토합니다. 개정안은 API 소비자 대표 팀을 포함한 리뷰를 거치며, 필수 규칙이 바뀌면 적용 시점을 최소 한 분기 전에 공지합니다.

## 부록: 신규 API 점검표

새 엔드포인트를 리뷰에 올리기 전 작성자가 확인합니다.

1. 경로가 kebab-case 복수 명사이고 버전이 첫 단계에 있는가.
2. 요청과 응답 필드가 모두 snake_case인가.
3. 에러 응답이 `code`, `message`, `trace_id` 세 필드를 갖추었는가.
4. 목록 API가 `cursor`와 `limit`을 받고 `limit` 최대값이 100인가.
5. 시각 필드가 UTC ISO 8601 문자열인가.
6. 생성성 요청이 `Idempotency-Key`를 지원하는가.
7. 요청 한도와 429 응답이 정의되어 있는가.
8. OpenAPI 명세와 계약 테스트가 함께 올라왔는가.

## 부록: 자주 묻는 질문

### 필드를 추가해도 버전을 올리지 않아도 되는가
그렇습니다. 소비자는 모르는 필드를 무시해야 하므로 필드 추가는 하위 호환 변경입니다. 다만 필수 필드로 바꾸는 변경은 새 버전이 필요합니다.

### 서비스 문서의 한도가 가이드와 다르면 어느 쪽을 따르는가
서비스별 문서가 우선합니다. 예를 들어 목록 API의 최대 크기는 서비스 특성에 따라 이 가이드의 100건보다 작을 수 있습니다.

### 내부 전용 API에도 같은 규칙을 적용하는가
적용합니다. 내부 API도 언젠가 외부에 노출될 수 있으므로 같은 규칙으로 만드는 편이 이후 비용을 줄입니다.

## 부록: 용어 정리

- 소비자: API를 호출하는 다른 서비스, 웹과 모바일 클라이언트, 외부 파트너를 모두 뜻합니다.
- 하위 호환 변경: 기존 소비자가 코드를 바꾸지 않아도 계속 동작하는 변경입니다.
- 계약 테스트: 소비자가 기대하는 요청과 응답 형태를 제공자가 자동으로 검증하는 테스트입니다.
- 커서: 다음 페이지의 시작 위치를 가리키는 불투명한 문자열 값이며 소비자는 내용을 해석하지 않습니다.

## 부록: 예외 승인 절차

필수 규칙을 따르지 못하는 사정이 있으면 예외 승인을 요청합니다. 요청서에는 예외가 필요한 규칙, 이유, 영향받는 소비자, 해소 계획과 기한을 적습니다. 아키텍처 리뷰가 매주 목요일 15:00에 열리며 승인된 예외는 명세 설명란에 승인 일자와 함께 기록합니다. 예외의 유효 기간은 기본 6개월이고 연장하려면 다시 승인을 받아야 합니다.

## 부록: 적용 우선순위

기존 API를 가이드에 맞출 때는 소비자 영향이 큰 순서대로 진행합니다. 에러 응답 형식과 인증 헤더가 가장 먼저, 그다음 페이지네이션과 날짜 형식, 마지막으로 네이밍을 정리합니다. 네이밍 변경은 필드 이름이 바뀌는 호환성 영향이 있으므로 새 메이저 버전에서만 적용합니다.
